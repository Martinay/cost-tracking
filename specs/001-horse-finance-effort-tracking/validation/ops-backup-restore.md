## Scope and limits

The dry run uses local temporary directories and both small synthetic JSONL and the existing canonical 17-variant event fixture. The restored fixture is byte-identical with its original hash, 17 events, final version 17, and all original event types; the integrated TestHost check additionally demonstrates API financial-report and pending-income replay parity after restore without reseeding. It compares aggregate report totals, stream version, and the digest of every pending-income key, verifies source bytes remain unchanged, and shows that a separate empty root is rejected without event-data repair. No Azure resource was provisioned. Independent storage failure domains, configured retention, live container shutdown, Azure SMB consistency, measured recovery time, scheduled backup-age loss, and billing remain unverified.

RPO arithmetic example only: with a last successful backup at `2026-10-08T12:00:00Z` and a hypothetical incident at `2026-10-09T11:59:00Z`, the age is 23h59m (1 minute below a 24-hour target). The manifest's `createdAtUtc` records an individual backup run, and `ops-restore-replay.json` records the local snapshot age of that one archive at verification; neither executes nor monitors a daily schedule. A missed backup can exceed 24 hours. Full T101 acceptance still requires schedule/retention evidence and a real restore from an independent failure domain.
